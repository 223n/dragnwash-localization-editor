# 事前調査レポート

翻訳者向けエディターをGo言語で構築するための事前調査です。

- 調査日: 2026年9月16日
- 調査の対象: [223n/dragnwash-localization](https://github.com/TomXV/dragnwash-localization)のコミット`003ed1e`時点
- 前提: 外部の翻訳コントリビューターへ配布します

## 結論

推奨する構成は、次のとおりです。

Goの単一バイナリがローカルの`HTTP`サーバーを起動し、既定のブラウザーを`UI`として使います。

理由は3つあります。

1. 翻訳者は世界中の言語を扱います。`IME`とRTLの両方に対応する必要があります。Goのネイティブ描画系`GUI`ライブラリは、この2点が未解決です。ブラウザーへ委ねれば、この問題は設計から消えます
1. `CGO`に依存しません。`GOOS`と`GOARCH`の指定だけで、9種類のバイナリを1台のマシンから作れます
1. エディターの`UI`自体を多言語にしやすくなります。配布先の翻訳者は日本語話者とは限りません

ただし、いきなり`GUI`を作ることは勧めません。

まず`CLI`ツールとして着手してください。

既存のビルドツールはWindows専用のPowerShellスクリプトと、Pythonに依存するスクリプトです。
macOSやLinuxの翻訳者は、コミット前のハッシュ化を実行できません。
この移植だけでも独立した価値があり、そのままエディターのコアロジックになります。

- ライセンス面の精査です。採用候補のライブラリはいずれもMITまたはBSD系と見られますが、未検証です

## 2. 既存リポジトリの仕様

エディターの設計を左右する制約を、既存の実装を読んで確認しました。

### 2.1 公開CSVは編集対象ではなく生成物です

`Translations/<locale>/strings.csv`は、一般的なCSVとして扱えません。

```csv
key,section,node,order,speaker,translation
# Language: 日本語 (ja)
# Created by ...

# ===== Level 1: Ryan (Sunny) | sets level_1 | ends level_1_complete =====
# --- intro: Ryan_1_intro ---
0da72197e898ebe1,L01 Ryan,Ryan_1_intro,1,Ryan,もしもし？
```

確認できた特性は次のとおりです。

- `#`で始まるコメント行と空行が混ざります。RFC 4180に準拠したパーサーは、これを解釈できません
- 行の並び順とコメントの見出しは、`data/script_order.csv`と`data/level_flow.csv`から毎回生成し直されます
- ヘッダーの直下にあるコメントだけは、最初のセクション見出しまで引き継がれます
- 訳が空の行は出力されません
- 英語の原文を含む`source_en`列を、公開ファイルに入れてはなりません。CIが検出して落とします
- 文字コードはBOM無しのUTF-8で、改行コードはLFです

つまり、Excelや一般的なCSVエディターで開いて保存すると、コメントの見出しが失われます。
専用のエディターを作る動機として、これが最も強い理由です。

### 2.2 キーの生成規則

`key`列は、英語の原文をUTF-8のバイト列と見なし、そのSHA-256の先頭16桁を16進数で表したものです。

Goでは次のように書けます。

```go
func KeyFor(source string) string {
    sum := sha256.Sum256([]byte(source))
    return hex.EncodeToString(sum[:8])
}
```

原文は一切加工されません。
前後の空白も残り、TextMeshProの書式タグも含みます。
`TranslationKey.cs`と`tools/hash-strings.ps1`の両方に同じ規則があり、Goでの再実装は容易です。

### 2.3 2種類のキー

| 形式 | 例 | 意味 |
| ---- | ---- | ---- |
| ハッシュ | `0da72197e898ebe1` | 同じ英文の台詞すべてに当たる訳です |
| 台詞ID | `line:6046bedf` | Yarnの台詞IDで示した1か所だけの訳です |

台詞IDの行は、複数のキャラクターが同じ英文を話す場合に訳し分けるためのものです。
エディターは両者を区別する必要があります。
台詞IDの行が空でも、警告を出してはなりません。

### 2.4 保存処理の実体

エディターの保存は、次の処理をすべて行います。

1. 編集中のデータを受け取ります。実体はキーと訳文の対応表です
1. 訳が空の行を除きます
1. `data/script_order.csv`の順に並べ替えます
1. セクションとノードの切り替わりで、`# =====`と`# ---`の見出しを差し込みます
1. 見出しの文言を`data/level_flow.csv`から組み立てます
1. `speaker`列に、同じ英文を話すキャラクター全員を`/`区切りで並べます
1. スクリプト順に無いキーを、末尾のUI用の見出しの下へ移します
1. 既存ファイルのヘッダー直下のコメントを引き継ぎます
1. カンマ、引用符、改行のいずれかを含む値を`"`で囲み、引用符を`""`へ置き換えます

これは`tools/hash-strings.ps1`の全面的な移植にあたります。
エディターのコアは`UI`ではなく、この再生成の処理です。

### 2.5 データの流れ

```text
[ゲーム内プラグイン]
   F1 -> Export working copy
        -> _discovered/<locale>.working.csv   原文つき・編集用・Git管理外
   F6   -> _discovered/dialogue_lines.csv     全会話文・実行順
   F7   -> _discovered/ui_texts.csv           全UI文言
   自動 -> _discovered/strings.csv            未翻訳の原文

[翻訳者]
   working.csv を編集して保存 -> ゲームが約2秒で読み直す

[コミット前]
   hash-strings.ps1      -> Translations/<locale>/strings.csv
   check-translations.py -> 形式の検証

[CI]
   GitHub Actions が check-translations.py を実行
```

エディターが担うのは、この図の「翻訳者」と「コミット前」の部分です。
ゲーム内プラグインの機能を置き換えるものではありません。

## 3. 機能要件の詳細

### 3.1 比較の対象は4種類あります

`_discovered/`配下には、性質の異なるファイルが4種類あります。

| ファイル | 列 | 性質 |
| ---- | ---- | ---- |
| `<locale>.working.csv` | `key,section,node,order,speaker,source_en,translation` | 編集の主な対象です |
| `dialogue_lines.csv` | `yarn_project,node,order,kind,speaker,line_id,key,source_en,translation,tags` | 会話文の全量です |
| `ui_texts.csv` | `key,source_en,translation,object_path` | UI文言の全量です。画面上の位置が付きます |
| `strings.csv` | `source_en,translation` | プレイ中に見つかった未翻訳です |

比較の機能としては、次の3つが実用的です。

1. 未翻訳の抽出です。ゲームが持つキーのうち、公開CSVに訳の無いものです
1. 孤児行の抽出です。公開CSVにあるものの、ゲーム側とスクリプト順のどちらにも無いキーです
1. 言語間の進捗比較です。13言語のうち、この言語にだけ欠けている行です

### 3.2 未登録には3つの意味があります

調査の結果、区別すべき状態が3つあると分かりました。

| 状態 | 検出の方法 | 翻訳者への示し方 |
| ---- | ---- | ---- |
| 未翻訳のキー | ゲーム側にあり、公開CSVに無い | 要作業として示します |
| 空の台詞ID行 | `script_order.csv`にあり、訳が空 | 正常です。訳し分けが不要なら空のままにします |
| 孤児キー | 公開CSVにあり、ゲーム側に無い | ゲームの更新で原文が変わった可能性として示します |

2番目を未登録として警告すると、約1900行のうち大量の誤検出が出ます。
仕様の上で、空の台詞ID行は正常な状態です。

### 3.3 最も価値の高い機能

ゲームの更新に追従する機能が、既存のツールでは手当てされていない領域です。

キーは原文のハッシュです。
原文が1文字でも変われば、別のキーになります。
ゲームが更新されると旧キーの行は孤児になり、訳が失われます。
いまは翻訳者が手作業で対応を探すしかありません。

エディター側で、孤児になった旧キーの訳と、新しく現れたキーの原文を突き合わせられます。
レーベンシュタイン距離などで並べ、引き継ぎの候補として示せます。

これは13言語すべてに関わるため、メンテナー側の負担も減らせます。

## 4. UIの方式の比較

### 4.1 比較表

| 観点 | A: ローカルWebとブラウザー | B: Wails v3 | C: Fyne | D: Gio | E: TUI |
| ---- | ---- | ---- | ---- | ---- | ---- |
| CGO依存 | 無し | 有り | 有り | 有り | 無し |
| クロスコンパイル | 1台で全OS分 | 各OS上でビルド | 各OS上を推奨 | 各OS上を推奨 | 1台で全OS分 |
| IME | ブラウザーに委ねる | WebViewに委ねる | 未解決の課題が有り | 限定的 | 端末に依存 |
| RTLの表示 | ブラウザーに委ねる | WebViewに委ねる | 描画のみ部分対応 | 描画のみ部分対応 | ほぼ不可 |
| 約1900行の表編集 | DOMで容易 | DOMで容易 | `widget.Table`が有り | 自前実装が必要 | 表示領域が厳しい |
| 実行時の外部依存 | 既定のブラウザー | WebView2とWebKitGTK | 無し | 無し | 端末 |
| UIの多言語化 | 容易 | 容易 | 可能 | 可能 | 可能 |
| 成熟度 | 標準ライブラリ | beta。GA未到達 | 安定。v2.8 | 安定 | 安定 |
| 開発の手間 | 中 | 中から大 | 小から中 | 大 | 小 |

### 4.2 A案はローカルのHTTPサーバーと既定のブラウザーです

Goの`net/http`と`embed`だけで完結します。
フロントエンドの成果物をバイナリへ埋め込み、`127.0.0.1`の空きポートで待ち受け、既定のブラウザーを開きます。
Syncthingやpprofと同じ方式です。

利点は3つあります。

- `IME`とRTL、フォント、アクセシビリティをすべてブラウザーへ委ねられます
- `CGO_ENABLED=0`のため、クロスコンパイルが容易です
- 標準ライブラリが中心のため、依存の陳腐化が起きにくくなります

欠点は2つあります。

- アプリらしさに欠けます。ブラウザーのタブとして開きます
- ローカルの`HTTP`サーバーとしての備えが要ります。第5.5節に挙げます

### 4.3 B案はWails v3です

見た目はA案と同じHTMLとCSSですが、専用のウィンドウで表示します。

ただし2026年9月の時点で`v3.0.0-beta.9`であり、GAに達していません。
公開されているリリース計画では、38個のゲートのうち27個が未解決のブロッカーです。

Linux版はGTK4とWebKitGTK 6.0が既定です。
ディストリビューションによっては、翻訳者側での追加インストールが要ります。
Steam DeckのSteamOSはファイルシステムが書き換えにくいため、実機での確認が要る領域です。

将来の有力な候補ですが、外部への配布を前提とする第1弾には早すぎます。

### 4.4 C案のFyneは候補から外れます

Go製の`GUI`としては最も成熟しており、`v2.8`が2026年7月に出ています。
しかし翻訳エディターという用途では、致命的な課題があります。

Issue [#618](https://github.com/fyne-io/fyne/issues/618)は2020年1月に作られ、2026年9月の時点で未解決です。
`IME`の変換候補がアプリの外側に出て、入力中の文字列がテキスト欄に表示されません。
原因は上流のGLFWの対応が進んでいないことにあり、Fyne側だけでは解決できません。

Issue [#2777](https://github.com/fyne-io/fyne/issues/2777)も未解決です。
中国語の入力中に文字列が切り詰められます。

日本語と中国語と韓国語の翻訳者が使う道具としては、この時点で採れません。
RTLに関するIssueは見つからず、機能として無い可能性が高い状況です。

### 4.5 D案のGioは手間が大きすぎます

描画層は`go-text/typesetting`を使います。
これはUAX #9というUnicodeの双方向アルゴリズムに沿って、文字列を分割できます。

ただし、テキストの入力欄でのキャレット移動や選択範囲の双方向対応は別の問題であり、検証が要ります。
またイミディエイトモードの`GUI`のため、表形式の編集は自前の実装が中心になります。

開発の手間が最も大きく、今回の用途には見合いません。

### 4.6 E案のTUIは外部配布に向きません

`CGO`が不要で配布しやすい点はA案と同じです。

しかし`IME`は端末エミュレーター側の実装に依存します。
Windows Terminalでは、`IME`の問題が長く報告されています。
また全角文字の幅の扱いに曖昧さがあり、原文と訳文を左右に並べる表示は崩れやすくなります。
RTLは事実上できません。

メンテナー専用の道具なら有力ですが、外部への配布には向きません。

## 5. 決定的な制約

### 5.1 IME

翻訳エディターにとって、これは前提条件です。
いまの翻訳言語13種のうち、`ja`、`ko`、`zh-Hans`、`zh-Hant`の4つが`IME`を必要とします。

確認できた事実は次のとおりです。

- Fyneは、Issue #618が2020年から未解決です。2026年9月にも更新されています
- Gioは、各プラットフォームのネイティブAPIを直に扱う設計ですが、実機での検証が要ります
- ブラウザーとWebViewは、OSの`IME`と統合済みです。追加の実装は要りません

### 5.2 RTL

`Translations/he/`としてヘブライ語が既にあります。

`RightToLeft.cs`を読むと、翻訳ファイルは論理順で保持され、表示のときにTextMeshProが反転させる設計だと分かります。

したがってエディター側の要件は2つです。

1. 論理順のまま保存します。並べ替えてはなりません
1. 編集中は視覚順で正しく表示します。翻訳者が読めなければ作業できません

1番目はどの方式でも満たせます。
2番目は双方向アルゴリズムの実装が要ります。
ブラウザーなら`dir="auto"`属性だけで済みます。

### 5.3 配布と署名

技術の選定とは別の、しかし見落としやすい問題です。

#### macOS

macOS 15のSequoia以降、右クリックからの「開く」による回避手順が廃止されました。
macOS 26のTahoeでは、さらに厳しくなっています。
署名の無いアプリケーションを開くには、システム設定から「このまま開く」を選ぶ必要があり、翻訳者への説明が煩雑になります。

恒久的な対策は、Apple Developer Programによる署名と公証です。
費用は年間99ドルです。

ただしA案のコマンドラインのバイナリであれば、`.app`形式の`GUI`アプリより回避手順が単純です。
`xattr -d com.apple.quarantine <ファイル>`の1行で済みます。
これも配布の方式を選ぶ材料になります。

#### Windows

SmartScreenの警告が出ます。
回避には署名の証明書が要ります。
OV証明書でも警告は完全には消えず、従来はEV証明書が必要とされてきました。
近年はAzure Trusted Signingという比較的安価な選択肢もありますが、要件は未確認です。

#### Linux

署名の仕組みは事実上ありません。
実行権限を与えるだけで動きます。

### 5.4 CGOとクロスコンパイル

`CGO_ENABLED=0`であれば、3つのOS向けのバイナリを1台のマシンから作れます。
対象はWindows、macOS、Linuxの`amd64`と`arm64`です。
GitHub Actionsのマトリクスビルドも要らなくなり、リリース作業が単純になります。

ネイティブ`GUI`とWebViewの埋め込みは`CGO`を必要とするため、各OS上でのビルドが要ります。

### 5.5 ローカルHTTPサーバーの備え

A案を採る場合、次の対策が要ります。
翻訳者のPCで動くため実害は限られますが、ブラウザーから届くサーバーである以上、最低限の設計は要ります。

- `127.0.0.1`にだけバインドします。`0.0.0.0`は使いません
- 起動のたびにランダムなトークンを作り、URLに含めます
- `Host`ヘッダーを検証します。DNSリバインディングへの対策です
- `Origin`ヘッダーを検証します。他のサイトからの要求を遮ります
- ファイルの読み書きを、起動時に指定したディレクトリの配下へ限ります

## 6. 推奨する構成

### 6.1 パッケージの構成

```text
dwloc（単一バイナリ）
├── cmd/dwloc/           CLIの入口
├── internal/csvfile/    コメント行を保つCSVの読み書き
├── internal/key/        SHA-256によるキーの生成
├── internal/order/      script_order.csv と level_flow.csv の解釈
├── internal/publish/    公開CSVの生成。hash-strings.ps1 の移植
├── internal/validate/   形式の検証。check-translations.py の移植
├── internal/diff/       作業コピーとの比較、孤児の検出、類似度の計算
└── internal/web/        HTTPサーバーと埋め込んだフロントエンド
```

コアの処理を`internal/`へ分けておくと、`UI`の方式を後から変えられます。
Wails v3がGAへ達したとき、`internal/web`だけを差し替える道が残ります。

### 6.2 ライブラリの選定

| 用途 | 選定 | 理由 |
| ---- | ---- | ---- |
| CSVの読み込み | 標準の`encoding/csv` | `Comment`にコメント文字を指定できます |
| CSVの書き出し | 自前の実装 | 既存の実装と同じ書き方を再現する必要があります |
| HTTPサーバー | 標準の`net/http` | 追加の依存が要りません |
| 静的ファイルの埋め込み | 標準の`embed` | Go 1.16以降の標準機能です |
| ファイルの監視 | `fsnotify/fsnotify` | `CGO`が不要です。ホットリロードとの連携に使います |
| 類似度の計算 | `agnivade/levenshtein` | 小さく、依存がありません |
| フロントエンド | 素のJavaScript | 約1900行なら仮想スクロールは要りません。ビルド工程を持たずに済みます |

Goの版は1.21以上で足ります。
ただし実装では、最新の安定版を使います。

### 6.3 段階的な計画

| 段階 | 内容 | 得られるもの |
| ---- | ---- | ---- |
| Phase 0 | CLIの`validate`と`publish`と`diff` | macOSとLinuxの翻訳者が、コミット前の処理を行えるようになります |
| Phase 1 | Web UIの一覧と編集と保存と検索と絞り込み | エディターとしての最小の構成です |
| Phase 2 | ゲームの更新への追従 | 他に代わりの無い機能です |
| Phase 3 | 配布の整備 | 外部への配布が実現します |

Phase 0だけでも独立した価値があります。

いま`tools/hash-strings.ps1`はWindows専用で、`tools/check-translations.py`はPython環境を前提とします。
Goの単一バイナリに置き換えれば、翻訳者は環境構築なしでコミット前の検証を行えます。
この段階で処理の正しさを確かめておけば、`UI`の実装のリスクも下がります。

## 7. 自作以外の選択肢

### 7.1 CLIツールだけに留める案

VS Codeなどの既存のエディターと、Phase 0の`CLI`ツールを組み合わせます。

- 利点は、実装の手間が最も小さいことです。翻訳者は使い慣れた道具を使えます
- 欠点は、コメントの見出しを壊す恐れが残ることです。原文との突き合わせも手作業になります
- 評価として、Phase 0を終えた時点で一度立ち止まり、これで足りるかを判断する価値があります

### 7.2 Weblateをセルフホストする案

翻訳のプラットフォームとしては実績があり、CSV形式にも対応しています。

しかし単言語のCSVを扱うには、`Monolingual base language file`が要ります。
つまり英語の原文の一覧を、サーバー上へ置く必要があります。
元のプロジェクトは「ゲームの英語の台本を再配布しない」ことを設計の中心に据えており、この方針と衝突します。

この案は採れません。

### 7.3 ゲーム内のエディターを広げる案

`Plugin.ImGui.cs`には、F1キーで開くツールウィンドウが既にあります。
ここにテキストの入力欄を足す案です。

- 利点は、原文が目の前にあり、反映も即座なことです。ファイルのやり取りが要りません
- 欠点は、UnityのIMGUIが日本語入力とフォントの埋め込みに弱いことです
- 欠点は、ゲームを起動しなければ作業できないことです
- 評価として、補助の機能としては有効ですが、主な作業環境には向きません

## 9. 主なリスク

1. 配布の壁が、技術の選定より大きくなる恐れがあります。macOSの署名が整わないと、開けないという理由で使われません
1. Phase 1以降の`UI`の実装に手間がかかります。負担が大きいなら、第7.1節の案で止める判断も合理的です
1. 公開CSVの生成規則が、C#とPowerShellとGoの3か所に散ります。差が出ると壊れたPull Requestの原因になるため、同じ入力に対して同じ出力になることを確かめるテストが要ります
